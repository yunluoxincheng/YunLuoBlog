> 对于刚开始学习部署的同学来说，网络知识往往是最容易卡住的地方。NAT、网关、桥接、Windows ICS、软路由、端口转发、内网穿透、反向代理、DNS、SSL/TLS 这些概念看起来彼此独立，但实际上它们都在解决同一个问题：**你的设备如何访问外部世界，以及外部世界如何访问你的服务**。
>
> 本文用一个统一的“代购”比喻，把这些概念串起来，帮助你从整体上理解现代网络部署的基本逻辑。

读完这篇文章，你会大致建立三条线索：

```text
设备如何访问外网
服务如何被外部访问
域名、反向代理和 HTTPS 如何组成完整访问链路
```

---

## 一、先建立一个“代购世界观”

我们把整个网络世界想象成一个“代购物流系统”。

| 网络概念 | 代购比喻 | 作用 |
|---|---|---|
| IP 地址 | 房间号 / 地址 | 标识一台设备的位置 |
| 端口 | 窗口 / 柜台 | 标识设备上的具体服务 |
| 私网 IP | 宿舍楼内部房间号 | 只在局域网内部有效 |
| 公网 IP | 公开收货地址 | 外网可以直接访问的地址 |
| DNS | 地图 / 电话簿 | 把域名翻译成 IP 地址 |
| 网关 | 宿舍楼出口 / 代购 | 当前网络访问外部网络的出口 |
| NAT | 代购用自己的身份帮大家下单 | 让内网设备共享外网出口 |
| NAT 表 | 代购的小本本 | 记录返回的数据应该交给谁 |
| 端口转发 | 固定转交规则 | 把外部访问转发给指定内网服务 |
| 内网穿透 | 长期热线 / 外部仓库 | 没有公网 IP 时让外网访问内网服务 |
| Windows ICS | Windows 自带的临时代购 | Windows 网络共享功能 |
| 软路由 | 专业代购中心 | 更稳定、可控的路由系统 |
| 桥接 | 每个人直接去外面登记身份 | 让设备直接接入上级网络 |
| 反向代理 | 大楼前台 | 根据域名或路径分发请求 |
| SSL/TLS | 加密信封和防伪印章 | 加密通信并验证身份 |
| HTTPS | 使用加密信封的 HTTP | 安全的网页访问协议 |

接下来，我们逐个拆解。

---

## 二、IP 地址：你在网络世界里的“地址”

IP 地址就像现实世界中的地址。

例如：

```text
192.168.137.2
```

可以理解成：

```text
宿舍楼内部 137 区 2 号房
```

这个地址只在你的局域网里有意义。外部互联网并不知道 `192.168.137.2` 是谁。

常见的私网 IP 包括：

```text
192.168.x.x
10.x.x.x
172.16.x.x ~ 172.31.x.x
```

这些地址就像“宿舍楼内部房间号”，只能在内部使用。

而公网 IP 则像真正对外公开的社会地址，例如：

```text
203.0.113.10
198.51.100.20
```

外部用户可以通过公网 IP 找到对应的设备或服务器。

---

## 三、端口：同一个地址里的不同“窗口”

一台服务器上可以同时运行很多服务。

例如：

```text
22    SSH 远程连接
80    HTTP 网站服务
443   HTTPS 网站服务
3000  前端项目
8080  后端接口
3306  MySQL 数据库
```

如果 IP 是一栋楼的地址，那么端口就是这栋楼里的不同窗口。

例如：

```text
192.168.137.2:3000
```

可以理解为：

```text
192.168.137.2 这台设备上的 3000 号窗口
```

所以访问一个网络服务，通常需要两个信息：

```text
IP 地址 + 端口号
```

也就是：

```text
找哪台机器 + 找这台机器上的哪个服务
```

## 四、DNS：网络世界里的“地图”或“电话簿”

我们平时访问网站时，很少直接输入 IP，而是输入域名：

```text
server.example.com
```

但是计算机真正通信时需要 IP 地址，所以浏览器会先询问 DNS：

```text
server.example.com 的 IP 是多少？
```

DNS 返回：

```text
203.0.113.10
```

然后浏览器再去访问这个 IP。

因此，DNS 的作用是：

```text
域名 → IP 地址
```

用代购比喻来说，DNS 就是地图或电话簿。

你问地图：

```text
server.example.com 这家公司在哪？
```

地图回答：

```text
它在 203.0.113.10 这栋楼。
```

注意：**DNS 不负责转发网页请求，它只负责告诉你地址。**

也就是说：

```text
DNS 不送快递，只告诉你快递该送到哪里。
```

## 五、网关：宿舍楼大门口的“代购 / 门卫”

网关是很多初学者容易混淆的概念。

一句话理解：

```text
网关就是你这台设备离开当前局域网时，必须先交给的“出口角色”。
```

继续用宿舍楼的比喻：

```text
你的电脑 / 服务器 = 宿舍里的同学
局域网 = 宿舍楼
同网段设备 = 同一栋楼里的其他房间
网关 = 宿舍楼大门口的门卫 / 代购
外部网络 = 校外商家 / 其他城市
```

如果你只是找同一栋宿舍楼里的另一个同学，例如：

```text
192.168.137.2 → 192.168.137.3
```

这就像你从 2 号房去 3 号房，直接在楼里找就行，不需要经过大门口的门卫。

但如果你要联系校外商家，例如访问：

```text
8.8.8.8
github.com
baidu.com
```

你的设备自己没办法直接把东西送到外面，于是它会先把请求交给宿舍楼大门口的门卫 / 代购，也就是网关。

假设你的 Ubuntu Server 配置如下：

```text
IP：192.168.137.2
子网掩码：255.255.255.0
网关：192.168.137.1
```

这句话翻译成“宿舍楼语言”就是：

```text
我住在 192.168.137.2 这个房间。
192.168.137.x 这些房间都和我在同一栋楼里。
如果我要找楼外的人，就把东西交给 192.168.137.1 这个大门口门卫。
```

所以，当服务器访问同网段设备时：

```text
192.168.137.2 → 192.168.137.3
```

它会直接在局域网内通信。

当服务器访问外部地址时：

```text
192.168.137.2 → 8.8.8.8
```

它不会试图自己直接把数据送到 `8.8.8.8`，而是先交给网关：

```text
192.168.137.1
```

这里有一个非常关键的点：

```text
目标地址仍然是 8.8.8.8，
但第一站先交给网关 192.168.137.1。
```

也就是说，网关不是最终目的地，而是“下一跳”。

用代购比喻就是：

```text
你最终想买的是校外商家的东西，
但你第一步不是直接冲到商家那里，
而是先把订单交给宿舍楼门口的代购。
```

在 Windows ICS 场景中，这个门卫 / 代购通常就是 Windows 笔记本。

例如：

```text
Ubuntu Server：192.168.137.2
Windows 共享网卡：192.168.137.1
```

这时 Ubuntu Server 的网关就是：

```text
192.168.137.1
```

完整链路可以理解为：

```text
Ubuntu Server
↓ 把外部请求交给宿舍楼门卫
Windows 笔记本共享网卡 192.168.137.1
↓ Windows 再把请求交给校园网
校园网网关
↓
互联网
```

所以，网关的本质不是“公网 IP”，也不是“DNS”，更不是“目标网站”。

它只是当前设备能够直接找到的那个出口角色：

```text
网关 = 当前局域网里，负责把你带到其他网络的门卫 / 代购。
```

这也解释了为什么网关通常必须和你的设备在同一个网段。

如果你的设备是：

```text
192.168.137.2/24
```

那么它能直接找到的通常是：

```text
192.168.137.x
```

所以网关可以是：

```text
192.168.137.1
```

但不能随便写成：

```text
10.88.1.1
```

因为 `10.88.1.1` 不在当前宿舍楼里，你连这个门卫在哪里都找不到。

用一句话总结：

```text
同楼的人，自己找；楼外的人，交给大门口的门卫 / 代购。
这个门卫 / 代购，就是网关。
```

## 六、NAT：代购真正开始工作

NAT，全称 Network Address Translation，中文叫“网络地址转换”。

它最常见的作用是：

```text
让多个内网设备共用一个外网出口访问互联网。
```

假设宿舍里有三台设备：

```text
A：192.168.137.2
B：192.168.137.3
C：192.168.137.4
```

它们都没有公网 IP，外部网站也不认识这些内部地址。

于是它们统一找代购，也就是网关设备，例如 Windows 笔记本、家用路由器或软路由。

A 想访问：

```text
8.8.8.8:443
```

A 发出的数据原本是：

```text
源地址：192.168.137.2:50001
目标地址：8.8.8.8:443
```

经过 NAT 网关时，网关会把源地址改成自己的外部地址：

```text
源地址：网关的外部地址:60001
目标地址：8.8.8.8:443
```

同时，网关在自己的 NAT 表里记一条记录：

```text
网关外部地址:60001 → 192.168.137.2:50001
```

当外部网站回复时，回复会先到网关。

网关查 NAT 表，发现：

```text
60001 是 192.168.137.2:50001 的请求
```

于是再把数据转交回 A。

这就是 NAT。

用代购比喻来说：

```text
内网设备 = 买家
NAT 网关 = 代购
外部网站 = 商家
公网 IP = 代购对外使用的身份 / 收货地址
NAT 表 = 代购的小本本
```

---

## 七、NAT 表：代购的小本本

NAT 表记录了“外部订单号”和“内部买家”的对应关系。

例如：

```text
外部表现                     内部设备
网关地址:60001       →       192.168.137.2:50001
网关地址:60002       →       192.168.137.3:50002
网关地址:60003       →       192.168.137.4:50003
```

外部网站只知道请求来自网关。

但是网关知道：

```text
60001 是 A 的
60002 是 B 的
60003 是 C 的
```

所以当回复回来时，它能把数据交给正确的内网设备。

这就是为什么多个内网设备可以共享一个外网出口。

---

## 八、为什么 NAT 后面的设备不能被外网直接访问？

NAT 的一个重要特点是：

```text
内网访问外网很容易，外网主动访问内网很困难。
```

原因很简单。

如果 A 主动访问了外部网站，代购的小本本里就有记录：

```text
60001 → A
```

外部网站回复时，代购知道该给 A。

但如果外部有人突然访问：

```text
网关公网地址:3000
```

代购一查小本本，发现没有对应记录。

它不知道这个请求应该交给：

```text
A？B？C？
```

所以默认会丢弃。

这就是为什么 NAT 后面的服务器，通常不能直接被外网访问。

更严谨一点说，外部主动访问失败通常不只是因为 NAT 表里没有记录，还和网关上的防火墙策略有关。很多家用路由器、校园网出口、公司网出口都会默认拒绝陌生的入站连接。

## 九、端口转发：给代购设置固定转交规则

如果你能控制 NAT 网关，就可以配置端口转发。

端口转发就是告诉代购：

```text
以后所有寄到 8080 柜台的包裹，都固定交给 A 的 80 号窗口。
```

网络里就是：

```text
公网 IP:8080 → 192.168.137.2:80
```

这样外部用户访问：

```text
http://公网IP:8080
```

路由器就会转发到：

```text
http://192.168.137.2:80
```

端口转发适合这种情况：

```text
1. 你有公网 IP
2. 你能控制入口路由器
3. 你能配置转发规则
```

例如家里宽带有公网 IP，并且路由器归你管理，就可以使用端口转发。

但在校园网里通常不行，因为学校的出口路由器不是你的，你没办法要求学校把某个公网端口转发给你的设备。

## 十、内网穿透：没有公网 IP 时的“长期热线”

内网穿透解决的是这个问题：

```text
我没有公网 IP，也控制不了上级路由器，但我仍然想让外网访问我的内网服务。
```

它的思路和端口转发不同。

端口转发是让外部请求直接打进来，而内网穿透是让内网设备主动连出去。

因为 NAT 通常允许：

```text
内网 → 外网
```

但不允许：

```text
外网 → 内网
```

所以内网穿透让内网服务器主动连接一台公网云服务器，建立一条长期隧道。

结构如下：

```text
用户
↓
公网云服务器
↓
内网穿透隧道
↓
本地内网服务器
```

常见工具有：

```text
frp
ngrok
cloudflared tunnel
nps
SSH reverse tunnel
```

另外，Tailscale 和 ZeroTier 也常用于解决“外部访问内网设备”的问题，但它们更像是虚拟局域网 / Mesh VPN 组网工具，和 frp、ngrok 这种端口映射式内网穿透不完全是一类。

```text
Tailscale
ZeroTier
```

用代购比喻来说：

```text
内网穿透 = 内网的人主动和外部仓库建立一条长期热线。
```

别人找你时，不是直接找你的宿舍，而是先找外部仓库。

外部仓库再通过这条热线把请求转给你。

这就是为什么在校园网、公司网、运营商大内网环境下，内网穿透比端口转发更实用。

## 十一、Windows ICS：Windows 自带的临时代购

Windows ICS，全称 Internet Connection Sharing，也就是 Windows 的“Internet 连接共享”。

它可以让一台 Windows 电脑把自己的网络共享给另一台设备。

典型结构：

```text
校园网
↓
Windows 笔记本
↓
Ubuntu Server
```

Windows 开启 ICS 后，通常会给共享网卡设置：

```text
192.168.137.1
```

下游的 Ubuntu Server 可能会获得：

```text
IP：192.168.137.2
网关：192.168.137.1
```

这时 Windows 笔记本就成了 Ubuntu Server 的网关。

它会帮 Ubuntu 做：

```text
DHCP 分配地址
NAT 地址转换
DNS 转发
网络共享
```

用代购比喻来说：

```text
Windows ICS = Windows 自带的临时代购服务
```

它的优点是简单，不需要额外安装系统。

但缺点也明显：

```text
稳定性一般
可控性较差
网卡变化后容易出问题
Windows 更新后可能异常
不太适合长期服务器环境
```

所以 ICS 适合临时共享网络，不太适合长期稳定部署。

## 十二、软路由：自己搭建的专业代购中心

软路由就是用普通电脑、服务器或虚拟机来充当路由器。

它可以做很多事情：

```text
NAT
DHCP
DNS
防火墙
端口转发
流量控制
多网卡转发
旁路由
透明代理
```

常见软路由系统包括：

```text
OpenWrt
iStoreOS
pfSense
OPNsense
Debian / Ubuntu 手动配置
```

如果把 Windows ICS 比作“临时帮忙代购的同学”，那么软路由就是“你自己搭建的专业代购中心”。

软路由的优点是：

```text
稳定
可控
日志清晰
规则明确
适合长期运行
适合服务器环境
```

对于本地服务器、[[Docker 容器化技术核心原理与实践|Docker]] 服务、校园网共享等场景，软路由通常比 Windows ICS 更可靠。

## 十三、桥接：不找代购，直接去外面登记身份

桥接和 NAT 是两种不同的网络模式。

NAT 模式是：

```text
宿舍里所有人都通过一个代购对外联系。
```

桥接模式是：

```text
每个人都直接接入外面的网络，自己登记身份。
```

例如：

```text
校园网
↓
桥接
↓
Windows 笔记本、Ubuntu Server
```

这时校园网可能会直接看到两台设备：

```text
Windows 笔记本的 MAC 地址
Ubuntu Server 的 MAC 地址
```

如果校园网限制只能一个设备登录，桥接可能更容易出问题。

所以在设备数量受限的校园网环境中，NAT 通常比桥接更合适。

简单总结：

```text
NAT：把内网设备藏在代购后面
桥接：让设备直接暴露给上级网络
```

## 十四、反向代理：云服务器大楼的前台

反向代理是部署网站时非常重要的概念。

常见反向代理软件包括：

```text
Nginx
Caddy
OpenResty
Traefik
Apache
```

假设你的云服务器上有多个服务：

```text
博客服务：127.0.0.1:3000
API 服务：127.0.0.1:8080
管理面板：127.0.0.1:8090
frp 映射：127.0.0.1:2005
```

用户访问的是域名，而不是这些内部端口。

例如：

```text
blog.example.com
api.example.com
panel.example.com
```

反向代理会根据用户访问的域名，把请求转发给对应服务：

```text
blog.example.com  → 127.0.0.1:3000
api.example.com   → 127.0.0.1:8080
panel.example.com → 127.0.0.1:8090
```

用代购比喻来说：

```text
反向代理 = 大楼前台
```

用户已经到了云服务器这栋楼，前台负责判断他要找哪个部门，然后把他引导到正确房间。

---

## 十五、DNS 和反向代理的区别：地图和前台

DNS 和反向代理看起来都像是在“指路”，但它们工作的阶段不同。

DNS 是地图：

```text
告诉你这栋楼在哪。
```

反向代理是前台：

```text
你到了楼里以后，告诉你该去哪个房间。
```

完整流程如下：

```text
用户访问 blog.example.com
↓
DNS 查询 blog.example.com 对应哪个 IP
↓
DNS 返回云服务器公网 IP
↓
用户连接云服务器
↓
反向代理根据域名转发到具体服务
```

所以：

```text
DNS：域名 → 入口地址
反向代理：域名 / 路径 → 后端服务
```

在常见的网站部署场景中，这个入口地址通常是公网 IP、负载均衡地址或 CDN 地址。DNS 不处理网页内容，反向代理才真正接收和转发 HTTP/HTTPS 请求。

---

## 十六、SSL/TLS：加密信封和防伪印章

HTTP 就像普通明信片。

它的问题是：

```text
别人可能偷看内容
别人可能篡改内容
你可能不知道对方是不是真网站
```

HTTPS 则是：

```text
HTTP + TLS
```

TLS 就像加密信封和防伪印章。

它解决三个问题：

```text
1. 防窃听：别人看不到通信内容
2. 防篡改：别人不能偷偷修改内容
3. 防冒充：证明你访问的确实是目标网站
```

证书就像官方发的身份证明。

当你访问：

```text
https://server.example.com
```

浏览器会检查：

```text
证书是否可信
证书是否属于 server.example.com
证书是否过期
```

如果都没问题，浏览器才会显示小锁。

严格来说，现在主流使用的是 TLS，SSL 是较早的旧称。

不过日常中大家仍然常说“SSL 证书”。

可以简单记为：

```text
SSL 是旧称
TLS 是现代版本
HTTPS = HTTP + TLS
```

---

## 十七、HTTPS 在部署链路中的位置

在实际部署中，HTTPS 通常由云服务器上的反向代理处理。

例如：

```text
用户
↓ HTTPS
云服务器 Nginx / OpenResty / Caddy
↓ HTTP
后端服务 / frp / Docker 应用
```

也就是说，外部用户到云服务器之间是加密的。

云服务器内部转发到本机服务时，可以使用 HTTP。这个前提是后端服务在本机回环地址、可信内网或受保护隧道里；如果中间经过公网或不可信网络，仍然应该继续使用 HTTPS 或其他加密方式。

典型结构：

```text
https://server.example.com
↓
Nginx 443 端口处理 TLS 证书
↓
http://127.0.0.1:2005
↓
frp
↓
本地 Ubuntu Server
↓
Docker 应用
```

这就是为什么反向代理经常负责 HTTPS 证书管理。

## 十八、把真实部署场景完整串起来

假设你的环境是：

```text
本地 Ubuntu Server
Windows 笔记本共享网络
校园网
云服务器
frp
域名
Nginx / OpenResty
Docker 服务
```

用网络语言表示：

```text
用户访问 https://server.example.com
↓
DNS 解析到云服务器公网 IP
↓
用户连接云服务器 443 端口
↓
Nginx / OpenResty 接收 HTTPS 请求
↓
反向代理转发到 frp 映射端口
↓
frp 通过隧道把请求送回本地 Ubuntu Server
↓
Ubuntu Server 转发给 Docker 应用
↓
应用响应后原路返回给用户
```

用“代购”语言表示：

```text
用户先查地图，找到公开仓库的位置。
到仓库后，前台判断用户要找哪个服务。
前台把请求交给一条长期热线。
热线连接到宿舍里的本地服务器。
服务器处理请求后，把结果沿着热线送回仓库。
仓库再把结果交给用户。
整个外部通信过程用加密信封保护。
```

这条链路里，每个概念都有自己的位置：

```text
DNS：告诉用户云服务器在哪
HTTPS/TLS：保证用户到云服务器的通信安全
反向代理：把请求分发到正确的后端服务
frp：把云服务器请求转回本地服务器
NAT/ICS/软路由：让本地服务器能够稳定访问外网
Docker：运行具体应用服务
```

## 十九、几个最容易混淆的概念对比

### 1. DNS 和反向代理

```text
DNS：告诉你去哪栋楼
反向代理：到楼后告诉你去哪个房间
```

DNS 负责域名到 IP。

反向代理负责请求到后端服务。

---

### 2. 网关和 NAT

```text
网关：负责带你离开当前网络
NAT：网关转发时，把你的内部身份换成它自己的外部身份
```

网关是角色。

NAT 是网关可能执行的一种地址转换技术。

---

### 3. NAT 和端口转发

```text
NAT：默认帮内网访问外网
端口转发：给外网访问内网开固定入口
```

NAT 默认适合“出去”。

端口转发是为了“进来”。

---

### 4. 端口转发和内网穿透

```text
端口转发：你能控制入口路由器
内网穿透：你控制不了入口路由器，于是主动连接公网服务器
```

家宽公网 IP 可以考虑端口转发。

校园网、公司网、大内网更适合内网穿透。

---

### 5. Windows ICS 和软路由

```text
Windows ICS：Windows 自带的简易临时代购
软路由：你自己搭建的专业代购中心
```

ICS 简单但不够稳定。

软路由配置复杂一些，但更稳定、更可控。

---

### 6. NAT 和桥接

```text
NAT：大家共用一个代购身份对外
桥接：每个人都直接暴露给上级网络
```

校园网限制设备数量时，桥接通常更容易出问题。

---

### 7. HTTP 和 HTTPS

```text
HTTP：普通明信片
HTTPS：加密信封
```

HTTPS 通过 TLS 提供加密、完整性校验和身份认证。

## 二十一、最终总结

如果只用一句话总结整篇文章：

> 本地服务器在内网里，就像住在宿舍楼里的同学；它要访问外网，需要通过网关和 NAT 代购；别人要访问它，因为代购默认不收陌生包裹，所以要么设置端口转发，要么让它主动连接云服务器做内网穿透；用户访问域名前，DNS 负责查公网仓库地址；请求到达云服务器后，反向代理负责分发到具体服务；HTTPS/TLS 负责保证外部访问过程安全可信。

理解了这条主线，再看 NAT、网关、DNS、反向代理、内网穿透、HTTPS，就不会觉得它们是零散的概念了。

它们共同组成了现代网络部署的完整链路：

```text
本地设备
↓
网关 / NAT / ICS / 软路由
↓
校园网 / 家宽 / 运营商网络
↓
云服务器 / 公网 IP
↓
DNS / 反向代理 / HTTPS
↓
用户访问你的服务
```

当你以后遇到网络部署问题时，可以沿着这条链路逐层排查：

```text
本地服务是否正常？
内网是否能访问？
网关和 NAT 是否正常？
服务器是否能访问外网？
内网穿透是否建立？
云服务器端口是否开放？
反向代理是否配置正确？
DNS 是否解析正确？
HTTPS 证书是否正常？
```

这样，复杂的网络问题就会变成一层一层可以定位的问题。
